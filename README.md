# Переобучение антифрод модели в Apache Airflow

## Входные данные
[Данные](https://www.kaggle.com/competitions/teta-ml-1-2025/data)

Поместите файлы в каталог проекта:

```text
data/train.csv
data/test.csv
```

## Быстрый запуск
1. Запустите Docker Desktop 
2. Поместите train.csv и test.csv в data
3. Создайте env и проверьте конфигурацию
4. Соберите и запустите стенд

```bash
cp .env.example .env
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 600
docker compose ps -a
```

Первая загрузка обрабатывает все строки и может занять несколько минут. Одноразовые volume-init, data-init, kafka-init, airflow-init должны завершиться с кодом 0. Веб сервер и scheduler Airflow должны стать healthy; scorer и simulator работать без циклических рестартов

| Сервис | Адрес или команда |
|---|---|
| Airflow | http://127.0.0.1:8081 admin / admin |
| Последний DQ отчёт | http://127.0.0.1:8082/latest.html |
| Все DQ отчёты | http://127.0.0.1:8082/ |
| Источник данных, версия и месяцы | docker compose exec scorer python scripts/inspect_state.py |
| Логи скоринга | docker compose logs -f scorer |

Отчёт появится после выполнения fraud_data_quality, до этого сервер отчётов может отвечать 404


## Ручная проверка
1. В Airflow дождитесь появления трёх DAG
2. Запустите supply_labeled_batch через Trigger DAG. При чистом запуске он добавит апрель 2020, перенеся даты выборки исходных строк в следующий календарный месяц. Если расписание уже успело сработать, целевой месяц будет более поздним.
3. Запустите retrain_fraud, первый кандидат проверяется на апреле 2019 его обучающие месяцы февраль и март 2019
4. После публикации выполните проверку Kafka, она берёт строку из test.csv, отправляет её с уникальным ID и ждёт результат с активной версией.
5. Запустите fraud_data_quality и откройте HTML отчёт. 

```bash
docker compose exec scorer python scripts/inspect_state.py
docker compose exec scorer python scripts/verify_kafka.py --require-trained
docker compose exec scorer ls -lah /shared/models
docker compose logs --tail=30 scorer
```


Посмотреть сообщения напрямую:
```bash
docker compose exec kafka kafka-console-consumer --bootstrap-server kafka:9092 --topic scoring --from-beginning --max-messages 5
```

## Архитектура и хранение
| Компонент | Назначение |
|---|---|
| data-init | Загружает train.csv порциями, создаёт начальную модель и указатель месяца |
| simulator | Непрерывно отправляет в Kafka транзакции из test.csv с новым ID и текущим временем |
| scorer | Читает Kafka transactions, применяет модель, пишет Kafka scoring |
| Airflow | Выполняет DAG поставки, переобучения и DQ |
| SQLite | Размеченная витрина, журнал запусков и указатели версий и месяцев |
| PostgreSQL | Служебная база самого Airflow с LocalExecutor |
| reports | Публикует HTML отчёты по HTTP |

Все контейнеры находятся в общей сети Compose. Том shared доступен по одному пути /shared в Airflow и скоринге.

| Путь | Содержимое |
|---|---|
| /shared/state.sqlite | Витрина, источник CSV, журнал запусков, активная версия, следующий месяц |
| /shared/models/model_<version>.joblib | Модель вместе с обученным препроцессингом |
| /shared/models/model_<version>.metrics.json | Метрики опубликованного кандидата |
| /shared/work/training/<run hash>/<month>/ | Окно, train, test, кандидат и решение проверки |
| /shared/work/supply/<run hash>/ | Подготовленные месячные батчи |
| /shared/work/dq/<run hash>/ | Компактные статистики снимка DQ |
| /shared/reports/ | HTML отчёты рядом с каталогом моделей |

Для экономии памяти CSV читается по 10 000 строк, в витрине сохраняются только используемые сырые поля и target. И Выборка для поставки и симулятора 
выполняется без загрузки всей витрины в память. DQ читает все строки порциями по 5000, сохраняет агрегированные статистики и не создаёт полную копию данных на каждом запуске.

SQLite работает в WAL на одном Docker хосте. Этот стенд не рассчитан на сетевую файловую систему или несколько Docker хостов. 
Все преобразования и inference работают на CPU. Зависимости обучения и скоринга закреплены в одном requirements.txt, включая dill==0.3.9 для загрузки файлов, сохранённых из Airflow.


## Месяцы и временное разбиение
При инициализации в витрину загружается весь train.csv. Начальное окно январь, февраль и март 2019. 
Параметры в .env:
| Параметр | Значение по умолчанию | Назначение |
|---|---:|---|
| batch_size | 2000 | Строк в добавляемом месяце, без возвращения и не больше размера витрины |
| window_months | 3 | Фиксированное число месяцев в окне обучения |
| history_months | 36 | Месяцев хранения, включая последний месяц |

window_months >= 2, history_months >= window_months. Размер окна и глубина истории сохраняются при инициализации;
Поставщик работает каждые 5 минут. 


## Собственный препроцессинг и модель
fraud_pipeline/features.py используется при обучении и онлайн через сохранённый sklearn Pipeline. 
Импутация, масштабирование и словарь категорий обучаются только на train. Классификатор LogisticRegression, class_weight=balanced, 
фиксированный seed, порог score >= 0.5. Проверочный месяц не используется при fit, ранней остановке или подборе гиперпараметров.

## Проверка качества модели
На одном и том же новом проверочном месяце из train.csv вычисляются ROC AUC и Average Precision для кандидата и действующей модели. 
Метрики разных месяцев напрямую не сравниваются. Публикация разрешена, только если обе метрики не ниже соответствующих метрик 
действующей модели. F1 при пороге 0.5 сохраняется для наблюдения и не участвует в решении.

Решение хранится в work/training/.../metrics.json. При rejected модель не публикуется, активная версия и next_month не меняются.
DAG при этом может быть зелёным: вычисления завершены, а проверка запретила публикацию. Новый запуск снова обрабатывает тот же месяц. 

## Повторы и обновление без перезапуска
Подготовка закрепляет за run ID целевой месяц и модель сравнения. Run-specific файлы повторно используются после ошибки. 
Поставка вставляет батч, удаляет старую историю и отмечает завершение одной транзакцией.

Публикация проверяет SHA256 кандидата и сохраняет файл через временный файл, fsync и os.replace. Только после этого одна 
транзакция SQLite обновляет активную модель, следующий месяц и статус запуска. Сбой до commit оставляет максимум файл без 
ссылки из реестра. Повтор старого успешного run не откатывает более новую модель и не двигает месяц второй раз.
Скоринг читает активную версию перед каждым сообщением, проверяет SHA256 нового файла и загружает модель без перезапуска. 
Модель и её версия заменяются вместе под блокировкой. При ошибке обновления уже работающий процесс сохраняет прежнюю модель
с её фактической версией, при холодном старте ошибка загрузки останавливает процесс.

## Контракт Kafka
- Вход: топик transactions, объект с transaction_id и data. data содержит исходные поля транзакции без target.
- Выход: топик scoring, массив записей, как в семинаре:

```json
[{"transaction_id":"tx-123","score":0.72,"fraud_flag":1,"model_version":"2019-04-012345abcdef"}]
```

Невалидные события попадают в scoring_errors. Входной offset подтверждается после подтверждённой доставки результата 
или ошибки. Доставка at least once: после сбоя между доставкой и commit возможен повтор с тем же ID. Версия доступна в 
Kafka, отдельный writer в БД условием задания не требуется.

## Data Quality
fraud_data_quality выполняется на минуте 2, 7, 12 и далее. Снимок согласован одной read-транзакцией, даже при параллельной 
поставке. Сначала формируются статистики и HTML, затем enforcement-задача завершает DAG ошибкой при нарушениях. 

| Правило | Критерий |
|---|---|
| Схема и непустая витрина | Все обязательные поля присутствуют, строк больше нуля |
| Пропуски | Нет null в обязательных полях |
| Уникальность ID | transaction_id не повторяется |
| Время | Все transaction_time разбираются как дата и время |
| Сумма | amount конечна и строго положительна |
| Координаты | Широты в −90…90, долготы в −180…180; значения конечны |
| Население | population_city конечно и неотрицательно |
| Метки | Только 0/1, оба класса представлены в каждом месяце |
| Месяцы | Нет пропущенных месяцев внутри доступной истории |

Обязательные поля используемые моделью сырые признаки из раздела входных данных, transaction_id и target. DQ проверяет 
размеченную витрину train.csv и дописанные месяцы, а не test.csv без меток. Отчёт показывает run ID, число строк, 
результаты и доказательства. Версионные отчёты сохраняются, latest.html содержит последний отчёт.

## Диагностика и остановка
```bash
docker compose logs --tail=100 data-init airflow-init airflow-scheduler scorer kafka
docker compose exec airflow-scheduler airflow dags list-import-errors
docker compose exec scorer python scripts/inspect_state.py
```

Если не найден CSV, проверьте наличие `data/train.csv`. Если 8081 не открывается, проверьте healthcheck и логи Airflow. 
При 404 отчёта сначала запустите DQ DAG. При отказе качества изучите metrics.json, указатель месяца намеренно сохраняется. 
После ошибки используйте Clear для упавшей задачи и downstream того же run, чтобы завершить закреплённый месяц. 
Если порт занят старым стендом, остановите его командой из раздела перехода.

Остановка сохраняет тома:

```bash
docker compose down
```
